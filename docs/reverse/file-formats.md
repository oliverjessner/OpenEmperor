# File formats

The read-only SG3 inspector follows the published [SG file-format notes](https://github.com/bvschaik/citybuilding-tools/wiki/SG-file-format) and the independently published [layout specification](https://github.com/hansonry/sgfileio/blob/master/sgSpecification.md) as references. Its C++ implementation is independently written. Both sources describe little-endian SG metadata and separate `.555` bitmap data; the latter documents 200 reserved group slots for SG3.

For versions 213 and 214, the parser recognizes an 80-byte header, a 600-byte index, 200 reserved 200-byte group slots, and an image table beginning at byte 40,680. Image records are 64 bytes in version 213 and 72 bytes in version 214. It reads the header's declared image capacity and active group count, then checks every table range against the actual SG3 file size before reading it. Bytes after the declared image table remain unparsed.

Known header fields read at offsets 0, 4, 12, 16, 20, 28, 32, and 36 are reported with their published names. Header bytes 8–11, 24–27, and 40–79 remain unknown. The reported SG file size is displayed beside the actual size; a mismatch is not silently normalized.

Each active 200-byte group record supplies a bounded filename (0–64), description (65–115), dimensions (116–123), image count (124–127), and first/last image indices (128–135). Bytes 136–199 remain unknown and are output as hex.

Each image record supplies documented data offset/length, uncompressed length at bytes 8–11, horizontal-mirror offset at bytes 16–19, signed dimensions at bytes 20–23, animation values, a **16-bit image type at bytes 50–51**, external flag at byte 52, isometric-size hint at byte 55, and group ID at byte 56. Version 214 adds alpha offset/length at bytes 64–71. The mirror offset is parsed and reported but not applied. Other undocumented spans, including bytes 53–54, remain explicitly unknown and appear as raw hex. The [layout specification](https://github.com/hansonry/sgfileio/blob/master/sgSpecification.md) documents these field widths; the older [SG notes](https://github.com/bvschaik/citybuilding-tools/wiki/SG-file-format) describe byte 51 and bytes 16–19 differently. We retain that source disagreement here rather than interpreting byte 51 as a compression flag or treating byte 53 as one.

For an internal image, the inspector checks the same-stem `.555` file. For an image whose documented external flag is exactly 1, it uses the named group file with a `.bmp` extension changed to `.555`, resolved under the SG3 directory. Other flag values or unsafe/unresolved names are reported without inventing a source path. The metadata-only command opens no bitmap payload; it checks file existence, file size, and both the stored and effective alpha ranges against that actual file size. An out-of-bounds stored range remains reported separately even when the selected effective range is valid; only the latter is read. No external offset correction is applied.

The selected-image loader and optional exporter accept plain image types 0, 1, 10, 12, and 13 when the selected payload has the required width × height × 2 RGB555 bytes; Sprite types 256, 257, and 276 use the documented Omega color stream. Type 30 splits its payload exactly at `uncompressed_length` into an uncompressed diamond-tile footprint and an optional Omega overlay. The documented classic tile is 58×30 (1,800 bytes), and the Emperor tile is 78×40 (3,200 bytes). The footprint occupies the bottom of the image and comprises N² sequential tiles in diagonal rows. The decoder requires the declared base size to equal `(width + 2) × ((width + 2) / 2)` and requires the geometry, size hint (if nonzero), dimensions, and complete tile count to agree; when the hint is zero it derives N only from a matching geometry and exact byte count. Omega skips preserve base pixels while literals overwrite them. No offset adjustment is inferred from observed anomalies.

Pixels use little-endian RGB555: red in bits 0–4, green in 5–9, and blue in 10–14 per the [layout specification](https://github.com/hansonry/sgfileio/blob/master/sgSpecification.md). The [SG notes](https://github.com/bvschaik/citybuilding-tools/wiki/SG-file-format) identify `0xf81f` as transparent. The shared conversion expands each five-bit channel to eight bits, emits row-major straight RGBA8, and sets alpha to zero for that transparent value. An explicit inspector export can write those bytes or package them as PNG following the [PNG specification](https://www.w3.org/TR/png-3/); PNG packaging adds no SG3 interpretation. The application can display the selected SG3 image directly in SDL3 without an export; its separate `--preview` path reads the project's exported PNG subset. Undocumented image types are rejected. The mirror offset is not used.

Version 214 stores `alpha_offset` at record bytes 64–67 and `alpha_length` at 68–71. The [published Omega description](https://github.com/hansonry/sgfileio/blob/master/sgSpecification.md) specifies `255, count` to skip pixels and any other command byte as the count of one-byte alpha literals. Only each literal's low five bits contribute to alpha; `(value5 << 3) | (value5 >> 2)` expands it to eight bits. Skips leave existing alpha intact, and literals replace A without changing RGB after color decoding. This stream algorithm has not changed.

The production addressing policy is narrowly based on the ignored Emperor GOG observations recorded in the research log. For a version-214, internal (`external_flag=0`), Type-256 image with `alpha_length>0` and **stored** `alpha_offset == data_offset + 2 * data_length`, the effective alpha range starts at `data_offset + data_length` and has length `alpha_length`. This equality is an observed profile marker, **not an interpretation of what `alpha_offset` originally means**. Checked 64-bit arithmetic computes the range; the actual `.555` file size governs every read. A zero `alpha_length` reads no alpha regardless of stored offset. Other alpha-bearing profiles are marked unverified and rejected by default, while explicit SPEC, CONTIGUOUS, LEGACY, and color-only diagnostic modes remain available. There is no automatic fallback or external `-1` production rule. Original external alpha images and pixel-exact comparison with the game remain unavailable.
