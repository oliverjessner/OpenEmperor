- Several documented external image offset/length pairs extend one byte beyond the corresponding observed `.555` file size. Some version-214 alpha offset/length pairs also extend beyond the observed internal `.555` size. The parser flags these ranges. Whether any of these fields use another convention is unknown.
- Pixel encoding, mirrored-image data, and all undocumented fields were outside this metadata-only stage.

## Image metadata audit and Omega Sprite stage

- The [published SG layout specification](https://github.com/hansonry/sgfileio/blob/master/sgSpecification.md) identifies bytes 50–51 as a little-endian 16-bit image type, bytes 16–19 as a four-byte horizontal-mirror offset, and bytes 8–11 as uncompressed length. An earlier parser treated byte 51 as a compression flag and byte 53 as another compression indicator. The parser now reads the type as 16 bits, preserves the mirror offset without applying it, and leaves bytes 53–54 unknown. This choice differs from parts of the older [SG wiki](https://github.com/bvschaik/citybuilding-tools/wiki/SG-file-format); it is not evidence of additional flag semantics.
- Independently authored Omega color decoding supports documented Sprite image types 256, 257, and 276. Synthetic tests exercise literals, transparent skips, row transitions, and malformed/truncated commands. No alpha stream is decoded.
- A local smoke test using ignored GOG data decoded a 32×32 Type-256 Sprite and displayed it in SDL3; Escape closed the window normally. The temporary visual check was deleted. No proprietary bytes or derived image files were added to the repository.
- A local inventory of 58 ignored SG3 files reported 63,709 Sprite-kind records and 4,114 Type-30 records. These are metadata record counts, not a claim that every payload is decodable; per-image bounds and unsupported alpha still govern loading.

## Version-214 alpha stream stage

- The [public SG layout specification](https://github.com/hansonry/sgfileio/blob/master/sgSpecification.md) documents separate alpha offset/length metadata at record bytes 64–71, one byte per literal alpha value (low five bits), and Omega skip/literal commands. An independently written decoder applies the exact documented five-to-eight-bit expansion to A only. The loader validates and reads the alpha range independently from the color range, including offset zero, then applies it after Plain, Sprite, or Type-30 color decoding. Synthetic streams and synthetic SG3/.555 pairs cover all three kinds, nonadjacent ranges, skipped existing alpha, truncation, and bounds rejection.
- Across 58 ignored local GOG SG3 archives, 9,059 records have nonzero `alpha_length`: 9,059 Sprite, zero Plain, and zero Type-30. Of these, 9,042 alpha ranges fit their actual `.555` file and 17 are out of bounds. None of the 17 is clamped, shifted, padded, or read.
- A read-only diagnostic applying the documented alpha command rules to the 9,042 in-bounds streams found 1,141 that are syntactically complete and 7,901 that fail a command or image-bound check. Syntactic completion does not establish correct visual semantics. Two real Sprite records from different archives passed the decoder, opened in SDL3, and exited normally with Escape, but both showed visible bands/holes. For one, a temporary build with alpha application disabled displayed a coherent color-only sprite, isolating the visible difference to the alpha path. That diagnostic change was reverted, and temporary window captures were removed. These observations do not justify an undocumented offset correction or a claim of full real-data alpha compatibility.
- No available Type-30 or Plain record has a nonempty alpha range, so real-data smoke tests for those combinations could not be run. Their support is synthetic-tested only. The meaning of the real-data alpha discrepancy, as well as previously observed one-byte out-of-bounds ranges, remains unresolved. Mirroring, maps, animation systems, and game logic remain outside scope.

## Version-214 alpha addressing audit

- Method: `openemperor-assets --data <ignored GOG data directory> --audit-alpha` scans every record with `alpha_length > 0`, checks both color and alpha ranges against the actual source file, and runs the documented Omega alpha command grammar over each readable candidate without rendering. The three independent hypotheses are SPEC (`data_offset`, `alpha_offset`), CONTIGUOUS (`data_offset`, `data_offset + data_length`), and LEGACY (`data_offset - external_flag`, followed immediately by alpha). Checked 64-bit arithmetic reports overflow and negative legacy starts; no invalid range is read. `--json` emits one metadata/diagnostic JSON object per record, including the exact failure, consumed bytes, advanced/final pixel cursor, and image pixel count. These diagnostics do not modify the production decoder.
- In the local ignored GOG set, 9,059 alpha-bearing records occur in 18 SG3 archives. All are internal (`external_flag=0`) Type-256 Sprites. There are **no real external alpha-bearing records** and no Type-257/276 alpha examples in this set. SPEC: 9,042 in bounds, 1,141 syntactically valid, **33 reaching the final pixel**, 7,901 malformed, 17 out of bounds. CONTIGUOUS: 9,059 in bounds, syntactically valid, **and reaching the final pixel**, zero malformed. LEGACY: the same 9,059/9,059 because its `external_flag` subtraction is zero for every observed record. The diagnostic uses the production parser's permissive end-of-stream rule, so a valid stream may stop before the final pixel; `complete` reports the stronger condition separately. There were no unavailable sources, arithmetic overflows, or negative starts in this set. The per-archive report is available from the CLI; no source bytes are printed.
- Metadata-only relationship: **all 9,059** records satisfy `alpha_offset == data_offset + 2 * data_length`; none has `alpha_offset == data_offset + data_length` or that value plus one. The most common `alpha_offset - (data_offset + data_length)` values are 256 (33 records), 3,472 (21), and 120 (10). The meaning of the observed factor of two is **unknown**; the audit does not rename or reinterpret the field.
- After the bulk pass, three internal Type-256 records were compared using temporary PNGs under `/private/tmp`: a 36×10 record, a 50×73 record, and a 236×263 record. Each was rendered with SPEC, CONTIGUOUS, LEGACY, and color-only. For the 236×263 sample, SPEC made 20,893 RGB-black pixels visible versus 561 for CONTIGUOUS, LEGACY, and color-only; in the 36×10 sample, SPEC made 114 RGB-black pixels visible versus zero for the other three. The CONTIGUOUS and LEGACY images were byte-identical in all sampled internal records and appeared spatially coherent. The 50×73 pair also showed substantially more unintended visible black under SPEC (1,139 versus 572). This is a limited visual comparison, not a reference-game pixel match. Temporary exports were deleted after review.
- Recommendation: the observed **internal** Emperor alpha payload starts at `data_offset + data_length`, supported by complete syntax across this local set and the visual samples. Keep production SPEC addressing and the README warning for now, as required by this audit milestone. The LEGACY external `-1` rule remains unverified on original alpha-bearing data; synthetic fixtures test its arithmetic only. Historical SGReader behavior is corroborating evidence, not the implementation specification. No proprietary bytes, rendered samples, or screenshots are committed.

## Narrow production integration of observed internal alpha addressing

- This milestone supersedes the previous audit-only restriction **only** for internal version-214 Type-256 records with nonzero alpha length and stored `alpha_offset == data_offset + 2 * data_length`. A pure shared layout function selects effective color `[data_offset, data_length]` and alpha `[data_offset + data_length, alpha_length]` using checked 64-bit arithmetic. The equality is an observed profile marker; the original meaning of `alpha_offset` remains unknown. The raw field is preserved and its bounds reported separately. A valid effective range is mandatory for reading; no clamping or fallback exists. Other alpha profiles, including external records, remain unverified in normal loading, while explicit diagnostic modes remain available.
- Synthetic regressions cover a distinct valid raw stream, a raw offset beyond EOF with valid effective alpha, an effective range beyond EOF on unverified metadata, malformed effective streams, external rejection, diagnostic SPEC preservation for previously separate alpha fixtures, and shared loader/catalog/inspector values. For the supported profile, a raw range can be out of bounds while the earlier effective range fits; the reverse cannot occur for equal nonnegative lengths in the same file. The reverse case is therefore exercised as an unverified record rejected by default and by an explicit CONTIGUOUS bounds check. Browser tests confirm supported alpha is visible by default, unverified alpha remains in the all-candidates view, and color-only mode has separate cache lifetime.
- A sequential, read-only run through the **normal full-image loader** over the ignored local GOG data found 9,059 alpha records, 9,059 matching the supported profile with valid effective color and alpha ranges, **9,059 successful RGBA decodes, zero failures**, and zero other alpha profiles. This is stronger than the earlier syntax-only audit. Fifty-two representative default/explicit-CONTIGUOUS RGBA pairs matched byte for byte in memory. The command wrote no image files and retained only the selected decode (and one comparison image when sampled).
- Separate visible SDL-browser checks used the normal browser with no alpha diagnostic flag. A first page of 20 internal alpha Sprite thumbnails from one archive showed zero failures, and the selected 58×72 image rendered in detail with the contiguous policy and effective offset. A second archive's 128×128 alpha Sprite page also rendered with zero failures. In a third archive, a 236×263 image previously affected by SPEC artifacts visibly rendered in detail with the contiguous policy. A 38×76 image whose **stored** alpha range is out of bounds but effective range is valid also rendered in browser detail. These are qualitative visual checks of actual SDL windows, not a pixel-exact reference-game comparison. The temporary test launchers and hard links outside the repository were removed; no screenshots or decoded pixels were committed.
- Remaining limits: the local set has no external alpha-bearing records and no alpha examples for Type 257, Type 276, Plain, or Type 30. The external `-1` hypothesis remains diagnostic only. The stored offset field's semantics, mirroring, and pixel-exact matching to the original game are unresolved. The historical audit above remains a record of the previous production behavior, not the current default.

## RGB555 channel correction and preview recheck (2026-09-17)

- The previous RGB555 conversion used red bits 0–4 and blue bits 10–14, following the [sgfileio Pixel Data table](https://github.com/hansonry/sgfileio/blob/master/sgSpecification.md). That table conflicts with the public [SGReader `SgImage::set555Pixel`](https://github.com/bvschaik/citybuilding-tools/blob/master/sgreader/sgimage.cpp), which masks red at `0x7c00` and blue at `0x001f`. Both references were viewed on their `master` branches on 2026-09-17; an immutable revision ID could not be retrieved in this environment. The shared independently written decoder now assigns red bits 10–14, green 5–9, blue 0–4. It still assembles source words little-endian, expands five bits with `(v << 3) | (v >> 2)`, treats `0xf81f` as transparent, and outputs straight RGBA bytes. SDL's [RGBA32 byte-array format](https://wiki.libsdl.org/SDL3/SDL_PixelFormat) receives those bytes without a compensating channel swap.
- A newly added fixed-vector regression failed against the old decoder: `0x7c00` produced the wrong RGBA order. After the correction, fixed red/green/blue/black/white/transparent and asymmetric `0x4a23 → (148,140,24,255)` expectations cover single pixels, explicit little-endian Plain bytes, Omega literals, Type-30 base and overlay, alpha composition, PNG, and a read-back SDL software surface. The alpha address and stream semantics were unchanged. A separate synthetic SG3/.555 export was decoded by the already installed FFmpeg PNG decoder; its two RGBA pixels were `ff0000ff` and `948c18ff`.
- From the ignored, user-supplied GOG data, path/index and supported metadata were checked before offscreen export. The corrected exports were visually viewed for Plain `DATA/China_General.sg3` image 253, Omega `DATA/China_General.sg3` image 603, Type-30 `DATA/China_Terrain.sg3` image 268, supported-alpha `DATA/China_Bodhidharma.sg3` image 1, and the former preview `DATA/China_Terrain.sg3` image 655. These were local offscreen image inspections, not interactive game-window tests or pixel comparisons with the original game. No local reference reader or original-game view was available.
- Image 655's earlier “flat sandy” appearance above was caused by the old red/blue assignment: it is uniformly pale blue with the corrected conversion. Image 268 is a visually plausible flat ochre ground tile and replaces 655 in the ignored `.local/terrain-bindings/preview.json` for the same exact raw pair `(128,0)`. Nearby images 640–670 include pale-blue and dark-teal tiles, but neither color nor adjacency verifies water semantics; no water binding was added. The image selection remains `curated_preview`, not a recovered original engine mapping. With the revised local binding, SDL dummy-driver runs report Xia 3,612 candidate / 1,905 bound / 1,707 unmapped, Banpo 6,384 / 4,538 / 1,846, and Chengdu 14,620 / 11,725 / 2,895; each reports one loaded asset and zero asset errors.
