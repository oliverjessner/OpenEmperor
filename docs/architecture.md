# Architecture

The optional macOS package changes the existing `openemperor` CMake target to
`MACOSX_BUNDLE` only in a separate Release configuration. The same `main.cpp`,
`Application`, `MenuSession`, map reader, renderer, `World`, and persistence
code run in both forms. A finite `--menu-check --app-root <fresh path>` mode
uses the real `MenuSession` with a dummy SDL renderer and injected temporary
storage for packaging tests; an optional `--data <path> --industry` exercises
the menu's Industry-v5 start, save, menu transition, load and resumed tick.
The ordinary app never selects that dummy driver or test storage. The normal
preference path remains SDL's `OpenEmperor/OpenEmperor` user folder.

`tools/package_macos.sh` builds and tests Release, stages only the installed
bundle, applies CMake BundleUtilities to its copied libraries, removes
absolute development RPATHs, adds dependency license notices, signs embedded
Mach-O files before the app, then verifies the recursive dependency graph and
relocated execution. `tools/verify_macos_bundle.py` is a fail-closed positive
file allowlist and dependency/signature checker. Synthetic fixtures and local
original-data smoke tests live outside the bundle. See
[macOS packaging](macos-packaging.md).

The application shell keeps command-line validation in `src/app/main.cpp`, SDL initialization and lifecycle in `src/app/Application.cpp`, and rendering in `src/renderer/TitleScreen.cpp` and `src/renderer/ImagePreview.cpp`. The shared asset library uses `src/assets/Sg3Archive.cpp` for independent, bounds-checked SG3 metadata parsing and type classification; `src/assets/Sg3ImageLoader.cpp` reads the metadata table, resolves safe `.555` paths, and independently validates and reads the selected color and alpha ranges. It dispatches plain RGB555 images to `Sg3RgbaDecoder.cpp`, Sprite types 256/257/276 to `Sg3OmegaDecoder.cpp`, and Type 30 to `Sg3IsometricDecoder.cpp`. The latter draws the validated diamond-tile base and applies an optional Omega color overlay into the same RGBA buffer. After color decoding, the loader applies an optional version-214 Omega alpha stream using `Sg3AlphaDecoder.cpp`; skips retain existing alpha and literals replace only the A channel. This library has no SDL dependency. The inspector uses `tools/asset-inspector/main.cpp` for command dispatch and `tools/asset-inspector/Sg3Inspect.cpp` for metadata JSON, compact summary, separate bitmap range reports, and optional exports; it calls the shared loader rather than owning runtime file-loading logic. `src/assets/RgbaPngEncoder.cpp` writes PNGs for inspection, and `src/assets/RgbaPngReader.cpp` reads this project's exported PNG subset for debugging preview.

Future game-data discovery and importing belong in `src/assets/` and `tools/importer/`. General reusable types belong in `src/core/`; platform-specific integrations belong in `src/platform/`. None of those modules contain game logic yet.

In explicit asset-preview mode, `--data` is checked and reported without entering the menu. With `--sg3 <file> --image <index>`, the app calls the shared asset loader, obtains one `RgbaImage`, uploads its pixels directly to an SDL3 texture, and renders it centered. No PNG, raw RGBA file, or inspector-tool dependency is involved. `--preview <exported.png>` remains available for debugging. SG3 inspection reports documented metadata and associated bitmap bounds; its export command can write raw RGBA bytes or a PNG when explicitly requested. The texture uses straight RGBA and SDL blending. Malformed or out-of-bounds effective alpha streams fail without fallback. External and otherwise unobserved alpha profiles remain unverified; see the research log. The parsed mirror offset is not applied. Reverse-engineering evidence belongs in `docs/reverse/`, separate from implementation.

`src/assets/AssetCatalog.cpp` scans a user-supplied directory without decoding pixels. It records stable `AssetId` values as relative SG3 paths plus image indices, established SG3/group fields, raw and effective alpha range statuses, and format support. Archives are sorted by relative path; malformed archives become errors while scanning continues. Directory symlinks and SG3 symlinks are not followed, and external `.555` paths reuse the loader's safe resolver. The `openemperor-assets` CLI filters records and emits a summary or metadata-only JSON without absolute local asset paths. Catalog `decoder_supported` includes the supported internal alpha profile; `color_decoder_supported` describes only the color layout.

`src/app/AssetBrowser.cpp` owns the SDL browser presentation. It starts from catalog metadata, decodes visible cells lazily through `load_sg3_image`, and uploads RGBA to nearest-neighbor SDL textures. A least-recently-used cache is bounded to 64 entries and 64 MiB, with a 16 MiB single-image limit. Decode errors stay attached to individual records and render as placeholders. The default view includes supported alpha profiles with valid effective ranges, excluding unverified ones; a toggle exposes all candidates. `--ignore-alpha` fixes color-only mode for the lifetime of its browser instance, so its cache cannot mix full and color-only textures. No image or thumbnail is written to disk, and the asset layer remains SDL-free.

`src/assets/Sg3PayloadLayout.cpp` is the pure shared decision point for effective ranges and the deliberately narrow alpha profile. Loader, catalog, and inspector call it; none mutates stored SG3 fields. For matching internal version-214 Type-256 records it selects contiguous alpha after color, conditional on the observed raw-offset relationship. Other alpha profiles have no production effective alpha range and fail normally. The catalog and inspector show raw and effective bounds separately; `decoder_supported` describes layout support, not range validity or actual decode success. `src/assets/Sg3AlphaAudit.cpp` remains a separate read-only research path for SPEC, CONTIGUOUS, and LEGACY comparisons. The explicit `--alpha-addressing` options override the production selection for a single diagnostic image; color-only `--ignore-alpha` is separate. `openemperor-assets --verify-alpha-decodes` runs supported records sequentially through the normal loader without writing pixels.

`src/scene/` defines an independently authored versioned JSON test scene and pure isometric projection/camera math. It validates relative SG3 AssetIds, source containment including symlinks and derived `.555` files, declared anchors and Emperor Type-30 footprints, grid/object limits, and duplicate IDs. This is scene-composition data, not reverse-engineered Emperor map data. `src/app/SceneView.cpp` handles time-based camera/input and window-to-render coordinate conversion as described in the [SDL3 high-DPI guide](https://wiki.libsdl.org/SDL3/README-highdpi); `src/renderer/SceneRenderer.cpp` owns a bounded cache of SDL textures keyed by distinct used AssetId. It draws terrain then stable depth-sorted objects with actual-image-rectangle culling, overlays the optional grid/selection, and presents once. Textures are destroyed before the SDL renderer. The SDL-free asset loader remains the only SG3 decoder. The small scene does not add map loading, a general scene graph, or simulation; see [scene format](scene-format.md).

`src/maps/EmperorContainer.*` independently parses the bounded outer block/zlib container, including validated multipart boundaries. It exposes physical block offsets separately from logical offsets in each decompressed part and checks exact zlib input/output consumption. `src/maps/EmperorMap.*` probes a part for the supported map signature and range profile, then returns raw little-endian terrain and object grids; the declared map size and unknown original-game active-cell status remain separate from the 228×228 storage dimensions. These libraries have no SDL dependency. `openemperor-map-inspect` performs deterministic, symlink-avoiding read-only inventory and emits independent container/map-read statuses with compact raw-value frequencies. `src/maps/StorageGridView.*` owns pure camera, picking, and raw-value color math. `src/app/MapDebugView.*` owns one SDL texture for raster diagnostics and separate renderers for curated and saved-ID texture modes. It does not use the JSON scene loader. The application resolves map paths under `--data`, requires explicit part selection for multipart files, and passes one verified map to the SDL view. Format evidence and limits are in [map-format notes](reverse/map-format.md).

`src/maps/TerrainInterpretation.*` overlays reference-derived bit/rule precedence on unchanged terrain/object words and reports recognized versus unknown bits, a coarse category, and partial status. `src/maps/MapGeometry.*` independently constructs the referenced diamond candidate mask for the five locally observed declared sizes and a clipped, reversible storage-cell-to-bitmap-pixel lookup; the off-map bit remains an independent signal. Distinct `GridCell` (storage), `BitmapPixel` (reference bitmap), and `DisplayCell` (camera raster) types make conversions explicit before SDL screen coordinates are used. `src/maps/MapVisualization.*` produces one compact diagnostic RGBA raster for raw, semantic, or projected view with optional candidate/off-map/comparison coloring. The SDL view caches interpretations once per map and updates its single texture only when the selected view, layer, or mask changes. Projection is the reference mapper's bitmap layout, not established game-world coordinates or an SG3 texture mapping. The inspector reports separate full-storage and candidate-mask semantic statistics, bounded unknown/partial combinations, and mismatch locations. These new interpretation and geometry layers remain SDL-free.

`src/maps/TerrainBindings.*` parses bounded local JSON that maps exact raw terrain/object pairs to validated relative SG3 `AssetId`s. It checks containment of both the archive and resolved `.555` file, Type-30 one-tile metadata, and declared payload bounds; it never contains map positions. `src/maps/TerrainRenderPlan.*` is the SDL-free material-selection and geometry layer: it emits one instance per candidate **storage cell**, retains raw/semantic diagnostics, records assignment status and counts, and uses an explicitly chosen 80×40 preview grid with a 78×40 image anchored at `(39,0)`. It does not reuse `projected_pixels`, whose two-pixel mapping is clipped at minimap edges. `src/renderer/TerrainPreviewRenderer.*` loads only distinct used assets through the ordinary loader, shares nearest-neighbor SDL textures, culls each instance against the viewport, and renders unbound cells as purple diagnostic geometry. `MapDebugView` retains its raw, semantic, and projected modes and owns the textured camera/input path; all drawing stays on the main thread, with one clear and present per frame. `asset_error` aborts loading rather than changing an explicit binding into a diagnostic placeholder. See [binding format](terrain-bindings.md). Original map structure, reference-derived categories, and hand-selected preview graphics are separate evidence layers; the original rendering rules remain unresolved.

`src/maps/GraphicsIdHypothesis.*` is the small, SDL-free, version-specific model for the observed generic EXE resource-ID split. It takes an explicit registration map; unknown slots and high-bit values never fall back to another archive. The current opt-in profile is `exe-6373328b-v213-runtime-table`; the older `exe-6373328b-14bit-hypothesis` name is rejected because it used an incorrect record skip. `RuntimeArchiveLayout.*` supplies the common version-213 system/dummy skip and physical-record translation to both this image-ID resolver and `ResourceGroupLookup.*`. Physical catalog `AssetId`s stay unchanged. `openemperor-map-graphics` retains the rejected direct-index H1 diagnostic and can decode selected profile samples. The saved map-word array's relation to the original game's first draw remains unverified; see [graphics-ID evidence](reverse/graphics-id.md).

`src/maps/StoredGraphicsPlan.*` retains one unchanged record per candidate storage cell, its saved word/byte and raw offsets, plus excluded-cell statuses. The shared `RuntimeArchiveLayout` resolves the studied v213 Terrain/Elevation records. A separate `PlacedFootprint` owns one or four cell indices and one physical asset; the default view creates only 1×1 instances. Explicit `--multi-tile-preview` accepts only isolated complete 2×2 components of identical saved IDs whose Type-30 metadata matches 158×at-least-80, 12,800 base bytes, size flag 2, and no mirror. The component's minimum coordinate is the rear/top **preview** origin; it is not a verified original anchor. The 2×2 image origin is `project(rear/top) − (width/2,height−80)`, while 1×1 remains `project(cell) − (width/2,height−40)`. Touching or incomplete groups remain diagnostic; candidate bytes are not interpreted. Raw map data and mask/off-map discrepancies are never rewritten.

`src/renderer/StoredGraphicsRenderer.*` runs on the main thread inside the existing `MapDebugView` camera and event loop. It validates required SG3 and `.555` paths under canonical `--data`, including symlinks, decodes each distinct eligible physical AssetId once, and shares one nearest-neighbor straight-alpha texture among placed instances. It draws each placed footprint once, with diagnostic cells remaining separate. The painter order uses the frontmost ground point, projected x, and stable source order for these simple, noninterlocking footprints; it is not a full original renderer. Culling and fit use each whole decoded image rectangle. Per-asset decode failure stays visible, with decoded and uploaded counts distinguished. Limits remain 2,048 distinct referenced assets, 16 MiB logical RGBA or payload per image, and 64 MiB summed logical RGBA textures, not a GPU-memory measurement. `MapDebugView` alone clears/presents, preserves ground-cell selection and raw reporting, and destroys textures before its SDL renderer. The curated `textured` path remains independent. The saved-ID snapshot and its opt-in preview placement do not resolve first-draw state; see [usage and limits](stored-graphics-preview.md).

The SDL-free `src/maps/MapSubtileMetadata.*` retains the original candidate byte while exposing a reference-derived 2×2 part position, marker candidate, and unknown high bit. `StoredGraphicsPlan` has separate `isolated` and `edge-byte` policies. The latter validates complete four-part claims by signed-calculated origin, saved ID, and physical AssetId before assigning ownership; touching instances can therefore remain distinct. It has no fallback to the isolated rule and does not change the shared renderer, image anchor, path checks, or texture cache. The marker is diagnostic, not an original-game draw command.

`src/maps/MapCatalog.*` performs deterministic, SDL-free standalone `.map` discovery, content probing, per-file error recording, and canonical path containment; the map inspector also reuses its standalone search. `src/maps/StoredMapSession.*` supplies the shared standalone saved-graphics load path for the browser, direct view, and render check. `src/app/MapBrowser.*` owns one current `MapDebugView` in the existing SDL window, while `Application` keeps a single main-thread event loop. Closing a map destroys its view and owned textures before another opens; no decoded-map cache accumulates. `src/app/MapRenderCheck.*` drives that same view through two bounded software-rendered frames without an interactive loop and reports separately on discovery, parsing, planning, decode/upload, coverage, and frame success. `tools/verify_map_corpus.py` only orchestrates the native catalog and rendercheck in isolated timed processes; it contains no map parser and writes incremental technical JSON under `.local/reports/`.

`StoredArchiveRegistrations.cpp` owns the parsed SG3 metadata, physical asset catalog, and `RuntimeArchiveLayout` for each explicitly selected slot. The base profile retains only slots 3 and 16. The separate `exe-6373328b-v213-slot8-runtime-table` profile conditionally adds slot 8 from `DATA/China_Mon_Earthen_Greatwall_1.sg3` when the map's candidate mask actually references it. The same collection feeds `StoredGraphicsPlan`'s image resolver; the map-graphics group query uses its named archive mapping and the same runtime layout. A missing optional archive, unsupported layout, unresolved index, available payload, and decoder outcome stay separate. Paths remain canonical under `--data`, including derived `.555` sources. The profile travels through direct viewing, browser sessions, headless reports, and the corpus runner without a second renderer slot list.

The opt-in `edge-byte-4x4` policy reuses the SDL-free saved-graphics planner and resolver. A size-parameterized geometry gate accepts only the supported 2×2 and 4×4 Emperor Type-30 dimensions, base lengths, size flags, valid source, and no mirror. Reference-derived part bytes propose a signed origin; all positions and competing claims are checked before any cell owns a footprint. The renderer decodes/uploads once per physical AssetId, draws the entire RGBA rectangle once per valid instance at `project(origin) − (width/2,height−40×side)`, and leaves all component cells individually selectable. Its front-ground painter order and large-image culling are preview conventions. Existing isolated and 2×2 edge-byte policies retain their previous behavior. The headless v2 report separates planned and rendered instances, unique covered cells, texture uploads, size histogram, and viewport draws.

The separate `sandbox-logistics-v1` mode loads a `StoredMapSession` with the explicit slot-8 and edge-byte-4x4 preview profiles. `src/maps/SandboxPlacement.*` converts the post-decode stored plan and existing candidate geometry into `sandbox_buildable_v1` without modifying original map words. `src/simulation/World.*` owns typed placements, bounded deterministic BFS routes, one courier, integer-tick production and transport, and the conservation invariant; it has no SDL or original-file dependency. `src/app/SandboxView.*` adapts SDL events and frame time, draws the shared `StoredGraphicsRenderer` background within the map clip, then primitive overlays and a compact UI before one present. `SandboxUiLayout` computes DPI-aware map/UI rectangles and hit targets without SDL; `RoadDrag` plans an X-then-Y path and commits a revalidated bounded command sequence through a temporary World copy. The UI keeps pointer gestures, tool, panel, hover and selection outside `WorldSnapshot`. Window-to-render conversion always occurs with the full viewport and unit render scale restored; the map clip does not change coordinates. The camera fits and centers in the free map rectangle, and only map points reach storage-cell picking. `src/renderer/StoredCamera.*` shares the existing stored-plan fit calculation with `MapDebugView`. The finite offscreen `SandboxCheck` uses the same view and core. These rules are our prototype rather than recovered original gameplay; see [sandbox behavior](gameplay-sandbox.md).

`World` also selects `sandbox-production-v2` explicitly without cloning the simulation engine. It retains the v1 tick path and shared fixed-step driver/BFS, while v2 uses fixed stable building IDs (Clay source, Pottery, Warehouse) and courier IDs (A, B). Storage occupancy records a building owner ID. Each courier owns its path, edge progress, cargo, reservation, and revision-keyed route cache; only placed roads connect its explicit source and receiver. The Pottery building keeps free Clay, Clay bound to one active recipe, and completed Pottery separately. The receiver holds reserved inbound space, which is not inventory. Both conservation identities and all capacities are checked at each integer tick. `SandboxView` draws both agents and the selected building's information from read-only state; its background and single-present composition stay shared. The v2 finite software check reports both couriers and actual deliveries using a versioned JSON schema. See [the authored rules](gameplay-sandbox.md).

`WorldSnapshot` is an SDL-free authoritative value type for both sandbox rule profiles. `World::restore` validates counters, placements, path geometry/progress, recipe and stock constraints, reservations, and balances before returning a fresh World; occupancy and owner indices are reconstructed, while future BFS caches are recomputed without touching active paths. `src/persistence/SandboxSave.*` owns the bounded versioned JSON document, map-relative identity, SHA-256 of the original map and post-decode buildability mask, and checked temporary-file replacement. The core has no filesystem or JSON dependency. `SandboxView` supplies the mask after background decode, swaps the World only after complete read/validation, pauses and resets its real-time accumulator, and reports F5/F9 results. The explicit finite resume check serializes to a temporary file, reparses, restores a fresh World, then compares every subsequent tick and rendered frames. This is OpenEmperor's own sandbox format, not Emperor savegame compatibility; see [schema and controls](gameplay-sandbox.md#openemperor-sandbox-saves).

The production profile now uses routing rule version 2 without changing its production timing. Its typed `RemoveRoad` command protects the occupied waypoint and both endpoints of a begun edge for each courier. A removed future segment is discarded immediately; the courier's phase, real waypoint or begun edge, cargo, reservation, pending-route flag, and last failed revision remain authoritative. The same deterministic BFS now accepts a placed-road start and an adjacent goal building, while new building-to-building dispatch still requires an intervening road. The route cache for future dispatch is separate from the active route. A courier waits at its actual cell after one failed search per road revision and resumes on a later topology change; return paths are reversed only if their entire old road sequence remains valid. `navigation_valid()` and the import validator check active suffixes and protected edges while allowing a removed historical road. Total road placements/removals and current roads establish the revision invariant after demolition.

For profiles v1–v4 the save adapter writes schema 4 and reads the known schema-1/2 logistics and production forms. Production schema-1 data is upgraded in memory to rule version 2 with zero removals and preserved active paths; no ticks or original file writes occur. `SandboxView` exposes the sixth tool and an orange waiting marker using only core state. The separate explicit `--sandbox-routing-check` uses an actually buildable original-map demo row and a temporary save, while the synthetic CTest case proves detour, waiting, repair, and deterministic continuation independently of original terrain. None of these routing rules asserts original Emperor behavior.

The opt-in `sandbox-household-v3` profile extends the same `World` and production tick path with a fourth fixed building and third fixed courier. The warehouse's existing Pottery stock is the supplier's only source; dispatch reserves household capacity, movement follows the same revision-aware BFS, and arrival deposits the cargo once. Household demand occurs between production and dispatch on every 400th tick after placement, using already stored Pottery. The authoritative household placement tick, progress, fulfilled/missed counts, last outcome, and consumed total are checked with the extended conservation identity. Schema 3 saves the full third route and household clock; schema-1/2 loads initialize those fields inactive without changing profile. The SDL overlay adds a seventh placement tool, a distinct house and courier, and state-backed inspector. The finite v3 check requires actual delivery, consumption, balances, three rendered couriers, and optional temporary-file continuation. All three profiles share the original read-only map background and conservative buildability mask; these housing rules do not claim original Emperor behavior.

The opt-in `sandbox-settlement-v4` rule version 1 generalizes the same SDL-free `World` to seven bounded building slots: production IDs 1–3 and stable household IDs 4–7. Placement allocates the next house ID only on success. One warehouse supplier retains a concrete target and its reservation during travel or waiting. At idle dispatch, a pure selector scans placed household IDs cyclically after the last successful dispatch, skipping full or unreachable houses. Four destination-specific route caches are keyed by road revision; an active path is not replaced by new placement. Each household owns its own stock, placement tick, demand clock, results, and consumed total. Production rates remain unchanged. The conservation check sums all household stocks and consumption. Schema 4 writes every building in ID order, the next household ID, round-robin cursor, three courier states, and active target; reads map records by ID and reject duplicates. Schema 1–3 readers preserve prior profiles and the original house ID 4. `SandboxView` shows four house rows and the actual supplier target; the headless check requires distinct real deliveries and consumption. These are authored sandbox rules, not original Emperor market behavior.

The opt-in `sandbox-industry-v5` rule version 1 extends the same World to nine bounded building slots and five couriers. IDs 1–7 retain their meaning from older profiles; IDs 8 and 9 are allocated in successful placement order and carry an explicit ClaySource or Pottery kind. Courier IDs 4 and 5 likewise store explicit Clay, Pottery or inactive roles, owner IDs and active targets. Production runs all placed Clay sources in ID order, then all Pottery works in ID order, followed by household demand, dispatch, movement and invariants. Each Clay courier has its own cyclic Pottery target cursor and per-target topology-revision route cache. Shared destination reservations equal the sum of all outbound shipments; arrivals release only their own amounts. The existing single household supplier and route interruption logic apply unchanged. Global production totals are checked against per-source extraction and per-Pottery recipe counters, inventories, cargo and consumption. Schema 5 writes nine canonical building records, five canonical courier records, next production/courier IDs and individual Clay cursors; the guarded schema-1–4 readers retain earlier profiles and their active paths. UI and offscreen checks read the same core state, while map cells and graphics remain read only. These are authored sandbox industry rules, not original Emperor economics.
# Menu and session lifecycle

The no-mode `Application` path owns one SDL window and one `menu::MenuSession`. Explicit CLI views and headless checks bypass this controller and never read personal settings or show dialogs. `MenuSession` owns the retained `SandboxView`; transitions occur after event polling. It renders a Loading frame before preparing a new map, decodes through the same `load_stored_map_session`/`SandboxView` path as `--sandbox`, and installs a candidate only after full initialization and optional dirty-session confirmation. A failed candidate leaves the previous World and textures alive. Menus do not feed time to the World, and the application resets frame time after load and I/O.

`MenuStorage` uses the existing map catalog, safe source resolution and sandbox save parser. Its separate bounded settings v1 file is atomically replaced under SDL's fixed `OpenEmperor/OpenEmperor` preference path; tests inject a temporary root. Save targets are unique and under its `saves/` child, outside the original data root. `MenuDialog` is an adapter for native asynchronous SDL folder/file dialogs. A callback copies its path into owned memory, sends it through a synchronized inbox, and never touches SDL views or textures. Numeric tokens in a synchronized registry prevent late callbacks from dereferencing destroyed views; generation checks ignore stale results. The menu scales its renderer coordinates with SDL window pixel density and converts pointer coordinates back through SDL. Tests inject a fake adapter and synthetic game-format bytes.
